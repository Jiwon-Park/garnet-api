# AGENTS.md

## Stack

- Single-binary Go 1.25 app using GoFiber v3 and `go-redis/v9` to talk to a Garnet RESP endpoint. All source is in `main.go`; there are no subpackages.

## Commands

- `go mod tidy` — keep `go.mod`/`go.sum` in sync before building.
- `go test ./...` — run all tests.
- `go run .` — start the server locally (listens on `PORT`, default 3000).
- `gofmt -l .` must return empty; CI fails the build on unformatted files. Match existing style (tabs, no trailing newline changes).

## Conventions that differ from defaults

- All HTTP handlers and Redis calls live in `main.go` — do not split into packages for small changes unless refactoring is requested.
- Config is read from env via `envString`/`envInt` helpers in `main.go:loadConfig`; `GARNET_PASSWORD` uses `os.Getenv` directly (empty string is valid).
- Access-refreshed TTL (`LRU_IDLE_TTL_SECONDS`) is intentional: Garnet config does not expose Redis `maxmemory-policy allkeys-lru`, so `GETEX` on get and `ttlForSet` on set provide LRU-style expiration when LRUIdleTTL &gt; 0. Do not replace with a Redis LRU policy.
- `LRU_IDLE_TTL_SECONDS=0` means **no expiration** — neither GETEX refresh nor per-key TTL is applied; keys live until explicitly deleted. Do not reintroduce a default TTL fallback.
- `setRequest.Value` and `TTLSeconds` are pointers so missing fields are distinguishable from zero values — preserve this when editing DTOs.
- API surface: `GET /healthz`, `GET /keys/:key`, `PUT /keys/:key`, `DELETE /keys/:key`. No translate endpoint — translation is handled client-side via `trans:`/`used:` key prefixes. Set values are capped at `maxValueLen` (1 MiB) and must be non-empty. Bump the constants when intentional.
- Logging uses stdlib `log/slog` (text handler, leveled). Do not reintroduce `log.Printf`.

## Release flow

- Releases are triggered only by pushing a `v*.*.*` tag (`git tag vX.Y.Z && git push origin vX.Y.Z`). CI builds linux amd64+arm64, publishes a GitHub release, then SSH-deploys and restarts the systemd service.
- Deployment requires GitHub Variables (`DEPLOY_HOST`, `DEPLOY_USER`, `DEPLOY_PATH`, `DEPLOY_SERVICE`) and secret `DEPLOY_SSH_KEY`; see `docs/github-actions-config.md` for the full list.
- Garnet itself is managed separately via the `Garnet Lifecycle` workflow (`install|start|restart|stop|status`), not by the release workflow.
- Garnet runs as a native binary under systemd (no Docker). The lifecycle workflow downloads `linux-<arch>-based.tar.xz` from the Garnet release, verifies SHA-256 against `GARNET_SHA256_X64`/`GARNET_SHA256_ARM64`, and installs the `GarnetServer` binary to `/opt/garnet/`. `GARNET_VERSION` is the tag without the leading `v`. To upgrade Garnet, update `GARNET_VERSION` plus both `GARNET_SHA256_*` GitHub Variables and re-run the `install` command.
- Persistent storage is on by default: `GARNET_ENABLE_STORAGE=true` adds `--aof --logdir <dir>` to the Garnet command and writes data to `GARNET_STORAGE_DIR` (default `/var/lib/garnet`). The systemd unit grants `ReadWritePaths=/var/lib/garnet`. Set `GARNET_ENABLE_STORAGE=false` for in-memory only.
- `GARNET_EXTRA_ARGS` cannot be empty (GitHub rejects empty vars); use `TODO_NONE` to mean "no extra args" — the lifecycle script skips it when set to that sentinel.

## Config reference

- `deploy/garnet-api.env.example` and `deploy/garnet.conf.example` are the source of truth for runtime env values and Garnet memory settings.
- The systemd unit is **not** checked in. It is generated by the `release.yml` workflow from `$DEPLOY_SERVICE` (unit name) and `$DEPLOY_PATH` (binary install dir) and installed to `/etc/systemd/system/${DEPLOY_SERVICE}.service`. The workflow also creates the `garnet-api` system user on first deploy and runs `daemon-reload` + `enable`. To change the unit's contents, edit the heredoc in the `Install systemd unit` step.
